# DocWen Assistant — Testing strategy

[简体中文源文](testing-strategy.zh-CN.md)

## Principles

Tests are separated by the evidence they can support. Source unit tests, mocked process integration, a fixed DocWen package, a real Obsidian host, manual Office checks, and public release state do not substitute for one another. Skips and external prerequisites remain unproven.

## Automated source tests

Vitest covers the fixed LOCALAPPDATA execution alias, rejection of PATH-relative launch targets, manual-path launch targets, the independent `gui open` control process and its CLI protocol-3 success envelope, connection cancellation and de-duplication, two-sided Machine protocol and minimum-product-version diagnostics, stale capability suppression, preload de-duplication and retry, connection-state migration and presentation, framing, Machine processes, cancellation, Bundle v3 validation and rejection of other schemas, capability projection, actions, Vault snapshots and transactions, settings, localization, runtime disposal, and release governance. Direct Markdown proofreading is locked to `validate.markdown` and `docwen.proofread_report.v2`, with an explicit non-regression check that it never passes through Markdown-to-DOCX post-processing. Settings cases prove pure, idempotent normalization, one-time unversioned migration, independently owned defaults, and zero startup or later writes for a newer schema while its unknown fields remain intact and the four-tab surface is visibly read-only. Resource tests cover cross-folder short Wiki links, filenames with spaces, repeated-occurrence deduplication, UTF-16-to-Unicode-code-point coordinates, missing/unsupported/over-budget resources, and the exact `neutral_document + numbering_export_plan` pair. Negative cases prove failure before task planning or writes and verify resource cleanup afterward. Machine lifecycle regressions also use a real native owner and controlled child on Linux x64/arm64 that closes its read end before query, task/execute, and accepted-task task/cancel writes. They observe actual written frames and EPIPE, prove there is no unhandled exception, bound waiter settlement, leave staging empty, and reap owned cross-session descendants. Dedicated Windows CI additionally uses real controlled processes and a native closed-stdin fixture to cover the old counterexample where the direct root exits normally while an independent-stdio descendant survives, plus timeout, accepted-task cancellation, plugin unload, real EPIPE, descendants that resist graceful completion, unrelated-sentinel survival, and fail-closed owner creation/embedded-PE identity failures before target launch. This process-level evidence still does not substitute for Obsidian host acceptance. Result-directory publication tests place a deterministic barrier between the final collision check and the publication primitive, then let an external writer create either an empty directory or a non-empty directory containing user bytes; both cases must reject, preserve target identity and user bytes, and clean only the request-owned staging directory. Source tests also pin the Linux x64 Node-API helper's public provenance, C-source SHA-256, embedded-binary SHA-256, and Node-API floor.

Proofreading lifecycle and view-state tests use a fresh happy-dom document with a small Obsidian DOM adapter. They dispatch DOM clicks and assert actual attributes, connected nodes, active elements and scroll state instead of inspecting recorded create-element calls. Integration cases exercise the real plugin saveSettings, ProofreadView and OperationCoordinator together, including initial empty state, same-generation cancellation, language changes, external focus and view closure/reopening. Large-report cases bound the initial DOM for 10,000 issues, reach every issue across batches, and verify keyboard focus, scroll, sorting, RTL localization, report reset and obsolete-control rejection. Existing source-digest and view-ownership cases remain in the suite. DOM fixtures do not establish browser layout or real-host acceptance.

Detected-format action regressions use a complete minimal DOCX fixture and the real Vault snapshot and capability-shape checks. They cover Cancel and Continue for a wrong extension, source kind changes in both directions, stale inspection/route facts, canonical-copy reinspection mismatches, cancellation, and source identity/content conflicts before publication. These unit cases mock Machine inspection and conversion. The fixed-package gate additionally runs the real export action, snapshot, client and exact Core process with a complete DOCX copied to `.txt`: Continue must produce Markdown with the expected paragraph and table, Cancel must create no canonical copy or output, and source changes at confirmation or review and replacement at review must prevent publication. The original fixture and unchanged source bytes are checked independently. UI dialogs are mocked in this package layer, which does not replace real-host acceptance.

Source regressions additionally cover closed-file stat/modify events after the last read, raw HTML literal ownership and real external resource identities in both resource scanners and the declared-input builder, including container boundaries, backticks in link destinations/titles, inline comments, reference images and code in image labels, formal health `status/reason`, exact recorded MSVC selection, and a legal 67-frame progress stream under byte, frame, random and merged stdout delivery. Linux x64/arm64 native CI reproduces the embedded owner twice and exercises setsid/double-fork descendants, root exit/crash, both supervisor crashes and a stopped pre-exec child after outer-owner death. Real process state, stopped heartbeats and unrelated-sentinel survival supply cleanup evidence; PID existence alone is insufficient. Source negative controls reject unknown architectures before image writes or spawn. Native adapter cases cover normal completion, abort, dispose, real query/task-execute/accepted-task-cancel EPIPE and unconfirmed-owner retry blocking; the retired JavaScript procfs/group path has no production entry. Topology fixtures use an explicit release to preserve the live baseline before normal exit or root crash; heartbeats and sentinels do not self-expire, and double-fork metadata is atomically published after closing the complete file. Per-case persistent diagnostics retain stages, streams/control, exit events, PID identities/states, metadata/heartbeat snapshots and original/cleanup errors; metadata and owner-close waits each retain six-second deadlines. These controlled native tests do not establish actual Obsidian, Gateway or Mermaid rendering acceptance.

Public conversion-client regressions validate the actual Bundle before publication and cover single DOCX/XLSX outputs, existing targets, an external file appearing after the final absence check, source guards, output-editor rejection, cancellation, changed parents, inconsistent flat Bundles, and complete Markdown directories with independently owned attachment resources. These source tests do not establish fixed-Core or Obsidian host acceptance. CSV is not an Assistant conversion target.

## Repository quality gate

Under the pinned toolchain, `npm run check` runs runtime verification, lint, formatting, README and stable-document contracts, coverage, type checking, build, artifact checks, and the high-severity dependency audit. Formatting and bilingual scripts read real repository content and are not placeholder no-ops. Artifact checking also verifies the Linux helper's pinned provenance and source/binary digests and requires the built `dist/main.js` to retain the exact embedded payload; this proves bundle inclusion, not Electron/Obsidian loading.

## Fixed DocWen package

`npm run acceptance:docwen-package` accepts only a full DocWen 0.17.0-or-later Windows package bound to a version, Candidate Bundle v3 identity, and digest. It verifies Machine health, capabilities, the exact v4 input pair, DocWen heading levels 1 through 9, both current footnote forms and the current endnote form, Obsidian-resolved embedded resources, Unicode/space paths, actual DOCX image bytes, complete `docwen.document_node.v1` publication, publication without node JSON and exclusion of linked images from business output counts, and successive exports into a chosen parent, and DocWen Bundle v3 write boundaries. Without the exact candidate identity it skips or fails closed and cannot be reported as source-suite success.

## Obsidian host

Real host acceptance covers the top-tab surface on the minimum Obsidian 1.12.7 host and a current 1.13.x host, each in a fresh isolated Vault and profile. It checks default and third-party themes, 16/20 px UI text, English and Chinese labels, narrow layouts, keyboard and RTL navigation, save-failure recovery, entry points, sidebar cancellation, file menus, zero process residue, and `data.json` preservation. Automated DOM tests do not replace those observations.

## Manual compatibility matrix

Windows manual checks cover Microsoft Store install, alias disable/enable, Store upgrade, uninstall recovery, portable fallback, DocWen GUI activation, native directory dialogs, Word/Excel/Markdown outputs, numbering conflicts, and visible proofreading. Separate Linux x64 manual checks cover manual package selection, Machine/GUI control, and real result-directory export; passing Ubuntu source CI for the Node-API helper and no-replace race does not substitute for real Obsidian Linux host acceptance. When Office or real-document rendering matters, the application version, sample, candidate digest, and human conclusion are recorded separately.

## Safe fixtures

Tests use synthetic files, temporary directories, and dedicated Vaults only. An ordinary or production Vault is never a test target, and real `data.json` is never deleted, overwritten, or reconstructed. Logs and failure fixtures sanitize paths, document text, executable locations, and credentials.

## Release evidence

The exact Candidate Bundle v3 digest, one isolated deterministic CI rebuild, candidate ZIP, `SHA256SUMS`, optional product evidence, event-bound authorization, tag binding, attestations, immutable GitHub Release, and remote byte readback are separate release evidence. An authorized stable version tag push triggers the verified publication workflow. Source verification binds source and `dist`; transport verification after download binds only Bundle bytes. Adapter, workflow-source, and failure-path tests prove only that the contract exists; they do not prove that GitHub executed it for the revision or that Community Plugins accepted it.
